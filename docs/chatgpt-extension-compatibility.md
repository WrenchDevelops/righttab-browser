# ChatGPT extension compatibility and migration boundary

Diagnostic date: 2026-11-05. Installed copy: ChatGPT 1.26.1102.11740, manifest V3, ID `hehggadaopoacecdllhhajmbjkdcmajg`. RightTab uses Electron 45.2.3 / Chromium 156.0.8078.80. The worker is `background.js`, and the default panel is `codex-work-sidepanel.html`.

## Observed behavior

In a fresh temporary Electron profile the unmodified installed copy loads and registers its service worker, but the worker logs **“Chrome extension background startup failed.”** Registration and a running worker process do not establish successful initialization. Electron reports unknown permissions including debugger, sidePanel, contextMenus and tabGroups. The existing settings record contained no runtime errors; RightTab observes extension page consoles, not service worker consoles. The startup log did not reveal an underlying exception, so its exact first failing call is unconfirmed.

Reproduce without using the browser profile: `npm run diagnose:extension -- /path/to/unpacked/extension`. This loads the specified extension unmodified in a disposable profile, waits eight seconds for worker console messages, and deletes the profile. A successful exit means the diagnostic completed, not that the worker initialized. The extension may contact its configured services during startup.

## Architecture decision

Electron explicitly supports only a subset of Chrome's extension APIs and states that arbitrary store-extension compatibility is a non-goal. Its main-process debugger is a CDP transport for a WebContents, not `chrome.debugger` inside an MV3 extension worker. A secure bridge would require extension-identity and permission enforcement, worker injection and event delivery, target lifecycle and session routing, as well as the many unrelated missing APIs above. Implementing only the first four namespaces would still leave startup and worker flows unsupported and would create a security-sensitive, version-dependent extension runtime. Do not enable a debugger bridge without permission enforcement, restricted target discovery and an always-visible disconnect control.

A maintainable route to investigate is a Chromium browser architecture retaining Chromium's extension subsystem, with RightTab's sidebar and UI integrated into that browser. A Chromium shell or embedding framework must be proven to retain the full browser extension system; Chromium rendering alone does not suffice. This is a substantial migration: build and update infrastructure, browser chrome and tab/window integration, extension install and permissions UX, persistent profiles and cookies, bookmarks, session restore, themes, startup settings, private-window isolation, panel/group UI, control indicators and Stop, and platform packaging all need design and validation. Native messaging also requires an explicit security and product decision; a full extension subsystem does not itself make a native host available. Authentication and service-side compatibility remain to be verified.

Preserve the current Electron app and data unchanged. Prototype the candidate in a separate executable and separate profile; add a reversible, read-only-first migration for settings, bookmarks and saved sessions, with explicit treatment of cookies, extension data and secrets. Before replacing RightTab, run the requested actual-extension end-to-end flow and restart/disconnect cases, verify permission boundaries, and obtain a decision on migration scope. No migration or API shim is implemented by this diagnostic.

References: [Electron extension support](https://www.electronjs.org/docs/latest/api/extensions), [Electron Debugger](https://www.electronjs.org/docs/latest/api/debugger), [Chrome sidePanel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel), [Chrome debugger API](https://developer.chrome.com/docs/extensions/reference/api/debugger).

## Separate Chromium experiment (2026-11-05)

An official Mac arm64 Chromium snapshot, revision 1737016, version 159.0.8146.0, was run in a new isolated profile, loading the installed extension unmodified. This is a full browser candidate; [current Chromium source implements the debugger extension API and its access checks](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/browser/extensions/api/debugger/debugger_api.cc). It is a development snapshot, not a built or branded RightTab fork. Full browser support is a candidate property, not proof of this extension's functionality.

Observed: Chromium loaded extension ID `hehggadaopoacecdllhhajmbjkdcmajg`, registered a worker target, and the extension opened the ChatGPT installation/login URL. A read-only worker evaluation showed `chrome.sidePanel`, `chrome.debugger`, `chrome.contextMenus`, `chrome.tabGroups`, `chrome.storage.session`, and `chrome.offscreen` objects, and `chrome.tabs.create` as a function. Presence does not prove correct behavior or error-free initialization; no capture of the worker's complete startup console was obtained. The user reported sign-in was rejected as insecure. The exact cause was not established and no restriction was bypassed. The ad-hoc-signed snapshot also logged missing WebAuthn keychain entitlement warnings.

Not verified: action/panel behavior, worker startup without exceptions, messaging/storage, authentication, actual browser control, extension context menu or groups, debugger attach/events/detach, disabling/re-enabling, and restart persistence. The snapshot is not a completed prototype interface and has Chromium's app identity. See [the experiment instructions](../chromium-prototype/README.md) for its launcher, pinned source-build configuration, profile isolation, and local test page. No data migration or user data changes were made.

## Authentication and control follow-up (2026-11-05)

The earlier report of an insecure-browser sign-in rejection is user-reported; the exact displayed message, rejecting provider, console/network details, and reason were not captured. The login entry point observed previously was a normal browser tab at ChatGPT's authentication page, but the rejecting screen itself was not observed. Do not attribute the reported failure to browser branding, extension ID, a missing API, or a provider restriction on this evidence. [Google's supported-browser guidance](https://support.google.com/accounts/answer/7675428) describes several possible causes, without establishing any of them here. [OpenAI's login guidance](https://help.openai.com/en/articles/7426629-why-cant-i-log-in-to-chatgpt) recommends using the account's original authentication method.

The existing Chromium experiment profile was still running with the pinned official Chromium snapshot 159.0.8146.0, `--user-data-dir` pointing to its separate prototype profile, `--no-first-run`, `--no-default-browser-check`, and `--load-extension` pointing to the unchanged ChatGPT extension. It was not launched with remote debugging for this run. On inspection the ChatGPT installation page and the extension's side-panel page were open; its embedded ChatGPT page displayed the Work composer. We did not establish which sign-in method was used or independently verify the account identity. The side-panel pin control worked. A local test page was served at `127.0.0.1:18765`, and the side-panel Work composer accepted a harmless task. The resulting conversation reached the extension's “Allow ChatGPT to use your Chrome?” prompt, explaining that it can read open tabs and take actions in them. At this point the test page was unchanged and the user was asked to choose whether to grant access. This demonstrates a live side-panel interaction but does not by itself prove worker startup was error-free, successful authentication, debugger attachment, or browser control.

No Chrome baseline, minimal-launch comparison, sanitized network/console capture, extension worker lifecycle test, context-menu, tab-group or restart test has been completed in this follow-up. Do not report the earlier authentication failure as reproduced or the local task as passed.

### Follow-up results after access was granted

The user granted the extension's browser-access prompt. In the same isolated Chromium 159.0.8146.0 profile, a manual end-to-end task using the unmodified ChatGPT 1.26.1102.11740 extension succeeded: the side panel submitted the request; the extension reported the local test page's heading; and direct visual inspection showed the page status changed to `Button clicked.` and the input contained `RightTab test`. In a second manual task, the extension opened another copy of the local page and created a group named `RightTab test` containing that tab. The extension reported that the group was blue; its color was not independently measured. These observations demonstrate actual browser control in this snapshot and this signed-in session, not in the Electron application or a branded RightTab fork.

During the group task Chromium displayed the native infobar `"ChatGPT" started debugging this browser` with a `Cancel` button; the infobar disappeared after the task ended. This is evidence of attachment and apparent automatic disconnection. The Cancel control and debugger protocol event delivery were not tested. A right-click on selected text displayed `Ask ChatGPT`; choosing it attached the selected text to the composer. Other context types were not tested.

The Chromium process was quit through its native menu and relaunched using the same separate profile and launcher. The ChatGPT extension remained pinned and its toolbar action opened the side panel. In `chrome://extensions`, switching the actual extension off and back on changed its enabled state and restored its toolbar icon. With developer mode enabled, inspecting its worker showed a console with one `[browser-tunnel] setup` message and no visible error at that moment; the entire startup log was not captured. A functioning post-consent task exercises messaging and storage indirectly but does not prove every API or event or persistent storage value. The same signed-in ChatGPT account's normal interface and conversation list appeared after the task; the login method and exact reported prior rejection are not yet known. The clean restart did not test restored tab groups or a control task after restart or re-enabling.

An isolated official Chrome 156.0.8078.80 process was started with a separate `chrome-baseline-profile` and no extension-loading or debugging flag. Loading the extension and authenticating in that baseline were not performed, so there is no controlled browser comparison yet. The original Chrome profile and original Electron profile were not modified by this experiment. A minimal-launch Chromium comparison, sanitized authentication console/network capture, an independent unauthenticated worker test, explicit user disconnect, protocol events, navigation/closure behavior, and verified extension behavior after re-enable remain outstanding. No reason for the previously reported sign-in error has been established.
